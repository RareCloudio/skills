# Trial log: the `ship-it` skill, November 2026

The skill was later renamed `devops`; this log keeps the name it had when the trials ran.

Skill version 0.1.0. The skill's text was tuned over seven advice passes on the same 35 apps; the pass graded below is the seventh, and the text published is that one plus the sentences section 1 describes. All sessions: Claude Code, model `sonnet`, started with `--setting-sources project --strict-mcp-config`, so no user settings or plugins were loaded. Real resources were created only on a dedicated test account and were deleted afterwards.

The raw answers, the blind keys and the graders' full reports are kept privately by the maintainers and are not in this repository. They are the model's words, not RareCloud statements.

## 1. The same question, with and without the skill

The question and the 35 open-source apps are those of the baseline in `evals/baseline/2026-11-11-no-skill/`:

> I want to put this app online: <link> . It works fine on my machine. What do you suggest, and how would you do it?

Each app was asked once without the skill (the baseline) and once with only the `ship-it` skill in the project's `.claude/skills/` folder. Both kinds of session could read the web and could not change anything. With the skill, the allowed tools were `Skill`, `Read`, `WebFetch`, `WebSearch` and `python3` for the skill's own scripts. No MCP server and no account in either.

The skill loaded in 35 of 35 sessions.

### Blind grading

Three separate grader agents (model `sonnet`, the same model that wrote the answers) each received a third of the 35 pairs, labelled A and B in random order, with no way to see which was which. They judged each pair as the person would experience it: advice right for the app, a clear recommendation with real alternatives, prices read from a source with a date, whether it moves the person forward, security and backups, tone and length, honesty.

Read the result as a sign, not a measurement: the graders are AI agents, the criteria are the ones the skill was written for, and the skill had been tuned on these same apps.

| | Pairs |
|---|---|
| Answer with the skill preferred | 33 |
| Answer without the skill preferred | 2 |
| Tie | 0 |

The two pairs the skill lost:

- a chat front end whose own project deploys free on a platform: the skill's answer led with a small paid server and put the free platform second;
- a WordPress project with a non-standard layout: the answer without the skill named that layout's own deployment tool and document root, and the skill's answer was a generic WordPress plan.

What the graders flagged, per side:

| Flag | With the skill | Without the skill |
|---|---|---|
| A wrong, invented or risky statement | 3 (two rated low confidence; the third is the price contradiction below) | 11 |
| Too long or too dense for a first answer | 5 (rated mild) | 15 |
| Too many questions, or questions already answered | 0 | 7 |
| A negative opinion about a provider with no source | 0 | 1 |
| Leans toward one provider | 9 (8 rated mild) | 0 |

The graders' summary of the answers without the skill: prices from memory as a range with no source or date, or no cost at all; a numbered install procedure that leaves the person to do the work; three or four questions; a few wrong on details that matter (a provider's outbound mail policy, memory sizing, whether an API key is needed).

Their summary of the answers with the skill: the project is read, the server is sized from the project's own files, prices are read that day from several providers, there is one clear pick and a real second option with when it wins, the trap that decides success is named, and the answer ends with what the agent needs in order to do the work itself.

### The nine "leans toward one provider" flags

This is the result we care most about, because RareCloud wrote the skill. Eight were rated mild and one was a real contradiction: an answer called RareCloud "the cheapest of the four I read" while its own list held a lower, unconfirmed price from another provider. The mild ones were of three kinds: RareCloud picked although a cheaper provider was listed, with "no contract" and "I can set it up through its API" given as reasons; a plan larger than a light app needs; and the paid server for the chat front end above.

After the grading, three sentences were added to the skill: that an agent can do the work through a provider's API is not a reason to prefer that provider; size from what the app's own documentation asks for; an app whose project deploys free on a platform, or a static site, gets that as the recommendation. The ten flagged or lost apps were run again and read by the agent session running the trials (not graded blind):

- every recommendation agreed with its own prices, or stated the fact that decided otherwise (a contract term read on the provider's page, a price that could not be confirmed);
- one answer recommended another provider outright because it was cheaper;
- every answer that listed RareCloud said once that the skill is published by RareCloud.

The six apps in the set that need no server of their own were then run once more: five were sent to a static host or a platform first.

Still not right after that: the chat front end was again given a server first; one answer still gave "I can manage it through its API" as a second reason beside a contract term; one answer said another provider "has a good reputation" with no source.

The wording changes made after the grading (sections above and the second review of the skill) were followed by one more run of all 35 apps on the final text. It was counted by text search and not graded.

|---|---|---|
| Names RareCloud at all | 33 | 29 |

Read in three of the final-text answers: one recommends another provider as the cheapest at the size it chose and lists RareCloud as the cheaper, smaller alternative; one recommends RareCloud on price and says it did not survey the budget providers widely; the chat front end is still given a small server first, with the comparison against a cheaper provider left open.

### Earlier passes, and what they changed

The first four passes were read and counted, not graded; each changed the skill's wording (prices missing, then answers too long, then the recommendation buried, then a comparison too narrow). The fifth was graded the same way as the seventh and was preferred in 34 of 35 pairs, but the graders found a negative remark about a cheaper provider, with nothing measured behind it, in about ten answers ("probably oversold", "in my experience"), and a recommendation of RareCloud against the answer's own price list in four. The skill was changed before the passes that followed: the recommendation has to agree with the prices read; no judgment on any provider's quality without a measurement or a cited source; the publisher is named whenever RareCloud is among the candidates. In the graded pass no such remark was found.

### One change after all of the above

In the passes above the skill told the agent to say once, whenever it listed RareCloud, that the skill is published by RareCloud. That sentence is in release 0.1.0 and was removed in 0.1.1: in answers it read oddly, and the repository and the skill's metadata already say who wrote it. The agent is told to say so plainly when asked. The counts of that sentence above describe the passes as they ran; no pass was run to measure the effect of removing it.

## 2. Real deployments on the test account

Three clean sessions, each with only the skill and the RareCloud MCP server (pinned 0.6.0) connected to the test account. The CLI was not allowed. Allowed shell commands were limited to `ssh`, `scp`, `curl`, `python3` and a few read-only ones. A snapshot of the account was taken first; after the trials the maintainers' cleanup script (kept outside this repository) deleted the three servers, the two SSH keys added by the sessions were removed, and a second run listed nothing left.

The agent session running the trials then checked every claim in each final answer from outside and on the server, as a separate step. No person re-checked them by hand.

| App | Request | What was built | Checked from outside | Result |
|---|---|---|---|---|
| A static site (a template's built files) | Exact: put it on a small server, no domain yet | Smallest plan, nginx, firewall, key-only SSH, automatic updates; build files left off the server | Home page and stylesheet answer, a missing page gives 404, the build files give 404, only SSH and HTTP reachable, password login off | Every claim held |
| A link shortener (PHP and MySQL) | Open question first, then "go with your recommendation" | Smallest plan, Caddy, PHP, MySQL; HTTPS with a real certificate on a free address derived from the IP; fresh secrets; private mode on; nightly database dump with one restore tested | Valid certificate, admin page answers, a test short link redirects, the config file gives 404, the database port is closed | Every claim held |
| An automation kit (n8n, Postgres, a vector database), without the local model | A budget and "pick the smallest that runs it comfortably" | The 4 GB plan with its price stated with and without tax; Compose with Caddy; the vector database no longer published; secrets generated on the server; nightly backup with a first run | HTTPS answers and HTTP redirects to it, the health endpoint answers, the five internal ports are closed, password login off | Every claim held |

What the sessions said they had not done, unprompted: backups still on the same server (two of three), no restore tested (one), no reboot tested (one), container images on a moving tag, no monitoring, a dependency audit not run, and two settings on the person's own account worth turning on. One session noticed that the account behind the token belonged to a different e-mail address than the person's and said so before going on.

What was not ideal:

- The static site was served over plain HTTP. The session said HTTPS needs a domain and did not mention an address that gives a certificate without one; the link shortener session did use one.
- The static site session offered to write the hand-over file instead of writing it. The other two wrote it next to the code, with no secret values.
- The automation kit got a self-signed certificate on the bare IP, said plainly, where the free address would have given a real one.
- One server relied on the cloud firewall alone, with no firewall on the host.

### When the access is missing

The first attempt at all three ran with a token the API refused. Each session stopped before creating anything, said so, still read the prices from the public catalog (which needs no token), described what it would do, and asked the person to put a new token in the environment, not in the chat. The sessions were then resumed with a working token.

## 3. Changes these trials call for

- Lead with the free platform when an app's own project deploys there, unless the person's need rules it out. Changed in wording; still missed once in the re-run.
- Know the less common layouts of well-known apps, or read their docs before giving a generic plan.
- Without a domain, prefer an address that gives a real certificate over plain HTTP or a self-signed one.
- Write the hand-over file every time.
