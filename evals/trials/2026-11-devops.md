# Trial log: the `devops` skill on real servers, November 2026

Run on 2026-11-12. Skill version 0.2.0 (worktree head `fd18f5a`), which still shipped helper
scripts; 0.3.0 removed them in favour of the real tools. Every session was Claude Code,
model `sonnet`, started with `--setting-sources project --strict-mcp-config`, in a scratch project
folder holding only the app and a copy of `skills/devops` in `.claude/skills/`. Sessions that
touched the cloud had the RareCloud MCP server (pinned 0.6.0) on a dedicated test account; the
RareCloud CLI was not allowed. Allowed tools: `Skill`, `Read`, `Write`, `Edit`, `Glob`, `Grep`, the
MCP tools, and `Bash` limited to `ssh`, `scp`, `rsync`, `curl`, `python3`, `docker`, `kubectl`,
`helm`, `nc`, `dig`, `ssh-keyscan`, `openssl`, `tar` and a few read-only commands. No web search or
fetch tool. `KUBECONFIG` pointed at an empty file, except in the cluster trial where it pointed at
that cluster's file.

The person's messages were written as a non-expert owner would write them. Follow-up messages are
quoted in each trial. The agent session running the trials checked every claim afterwards from
outside and on the server, as a separate step, and recorded the command and output. No person
re-checked them by hand. Raw session output, the verification transcripts and the generated files
are kept privately by the maintainers.

Addresses and names that identify the account are written as `<server>`, `<ip-name>.sslip.io` and
`<lb-ip>`.

## Trial 3: the site is down

Each breakage was a fresh session in a copy of the trial 1 project folder (with its hand-over), the
account connected, SSH access. Message both times: "My site is down since this morning. Can you
look?" plus the key path and options.

**3a, upstream port changed.** The runner changed the Caddy upstream in the server's Compose file from
`app:8000` to `app:8080` and recreated Caddy: `/healthz` gave 502. The session read `outage.md`,
reproduced the 502 from outside, found the cause in about a minute (the server's file differs from
the local one in that line; the Caddy log shows `dial tcp ...:8080: connection refused`), noticed the
file's change time did not match "since this morning", and asked before touching the live server.
Reply: "Hm, maybe that was me yesterday, I was trying something. Yes, go ahead." It backed up the
broken file, put the local one back, saw that `up -d` did not recreate Caddy, forced it, and checked
from outside. 15 tool calls, under 2 minutes.

**3b, database stopped and its restart policy removed.** The runner ran `docker update --restart=no`
and `docker stop` on the database: `/healthz` gave 503. The session reproduced it from outside, found
the stopped container, then read the server's sudo log and found the exact commands, the user, the
key and the source address, with times. It stopped, said this could be the owner or a compromise
(and what to rotate if so), and noted that the times did not fit "since this morning". Reply: "Oh,
that was me messing around earlier, sorry, I got the time wrong. Yes, start it and put the restart
policy back." It did, and checked from outside. 11 tool calls, under 2 minutes.

## What was not ideal

- **fail2ban said one hour, ran ten minutes** (trial 2). The jail was written after the package had
  started fail2ban, and `enable --now` does not reload a running service.
- **The owner's own address got banned.** The deliberate failed logins that prove root and password
  are refused come from the person's address, and they count toward fail2ban. Here they were added to
  the runner's checks; an owner who mistypes once afterwards gets the same.
- **Trial 1 waited about 100 minutes on a broken package mirror** and only switched mirrors when
  asked how it was going. Trial 2 diagnosed the same mirror in ten minutes.
- **The hand-over's password-change step probably does not work.** The proxy config is inline in
  Compose `configs:` (as in the skill's template). Changing it and running `docker compose up -d`
  did not recreate Caddy. Trial 3a found this; trial 1's hand-over still gives the plain `up -d`.
- **The first answer in trial 1 said "HTTPS needs a domain."** The same session later used an
  IP-derived name with a real certificate, which `web-and-https.md` describes.
- **The cluster trial skipped the config check and the templates.** The manifest was written from
  memory, applied without `check_config.py`, and runs the pod as root. The context name was not said.
- **Trial 5 left the Dockerfile unlinted** though Docker was on the machine. `check_config.py` said
  Docker was "not allowed", and the session read that as a reason to stop.
- **The MCP create result carries the server's console password.** It went into the session's
  transcript. The session did not repeat it, store it or mention it in the hand-over.
- **Trial 1's restore test ran a `delete` on the live table in the same command as a restore that
  failed.** It was only its own test row.
- Many tool calls were refused by the narrow allowlist (`cd` with redirects, variables, `sleep`
  loops): 2 to 5 per turn. That is this setup, not the skill. It slowed the waits in trial 4.
- Prices from other providers could not be read (no web tool). Trial 1 named alternatives and said
  it had not read their prices.

## What the trials say should change in the skill

1. `templates/fail2ban-sshd.local` and `references/server-hardening.md`: after installing the jail,
   `systemctl restart fail2ban` (the package starts it with defaults), then read back
   `fail2ban-client get sshd bantime` before claiming a value.
2. `references/server-hardening.md` and `references/proving-it-works.md`: run the failed-login
   proofs before enabling fail2ban, or unban the address afterwards
   (`fail2ban-client set sshd unbanip <addr>`), and say in the hand-over that a few mistyped logins
   lock the person out for the ban time.
3. `references/updates.md`: when apt is slow, time the configured mirror against
   `archive.ubuntu.com` within the first minutes and switch with the original kept, instead of
   waiting. Do not say who runs a mirror unless you checked.
4. `templates/compose.yaml` and `references/docker.md`: say that a change to an inline `configs:`
   block, or to a `.env` value used in it, needs `docker compose up -d --force-recreate caddy` (or a
   bind-mounted Caddyfile and `caddy reload`). Hand-overs that tell the person how to change the
   password or the address must use that command.
5. `references/kubernetes.md`: make the template and `check_config.py` steps part of the deploy
   sequence for a quick "deploy this and give me a URL", not only for a full first deploy, and keep
   the `securityContext` when the image allows it. Repeat that the context is said in the answer.
6. `SKILL.md` ("Writing configs") or `scripts/check_config.py`: when Docker is present, rerun with
   `--allow-docker` for files you wrote yourself; make the script's skip message say that.
7. `SKILL.md`, open question: when there is no domain, mention the IP-derived name with a real
   certificate in the first answer instead of saying HTTPS needs a domain.
8. `references/rarecloud-safety.md`: a create result can carry a console password; keep it out of
   the answer, store it like any other secret, and mention it in the hand-over.

The skill was changed along these lines after the trials. Each code and config change was run in
local containers; the wording changes (the hand-over rule, the no-domain sentence, the cluster
path) are text and were not. Three came out differently from the list. Running the refusal checks
before fail2ban does not help, because fail2ban reads back the last ten minutes of the journal
when it starts; the address the work comes from is exempt while the server is set up, through a
drop-in that a timer removes. Caddy's config
moved out of the Compose file into a Caddyfile in a mounted folder, applied with a graceful
reload. And item 8 went into the skill's general rule on credentials, since it holds for any
provider.

Outside the skill: the public catalog showed no price for the load balancer, and the package mirror
the Ubuntu image came configured with failed on the day.

## What was not tested

A real domain and DNS change, e-mail, CI/CD pipelines, a service without containers (systemd),
monitoring and alerts, scaling to several servers, backups off the server, Debian or Rocky images,
a server someone else had already set up with live traffic, a full disk, Kubernetes with ingress,
HTTPS or several services, other coding agents, and any provider other than RareCloud. Each trial
ran once; nothing here measures how often the same result comes back.

## Spend and cleanup

Resources created: three Cloud VMs (trial 1, trial 2, and the cluster's worker), one managed cluster,
one load balancer and one 2 GB volume made by the cluster, one SSH key on the account (trial 2). All
priced hourly: about 3.7 VM-hours of the smallest plan, 0.8 hours of the cluster's worker and a
quarter hour of the load balancer, paid from the test account's bonus credit. Nothing prepaid.

Deleted as each trial ended: the cluster's namespace (load balancer and volume) and then the cluster
after trial 4, the trial 2 server and its SSH key after trial 2. The trial 1 server was deleted by the
maintainers' cleanup script after trial 3. A second dry run of that script listed nothing, and a new inventory matched the one
taken before the trials (two firewalls and the default network); the volume, snapshot, load balancer,
reserved IP, SSH key and object storage key lists were empty, the two pre-existing firewalls had the
same rules and nothing attached, no billing alert or ticket was created, and quota usage was back to
its earlier figures.
